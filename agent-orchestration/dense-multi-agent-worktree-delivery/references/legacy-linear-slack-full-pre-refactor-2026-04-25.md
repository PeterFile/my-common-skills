# Linear + Slack + worktree delivery loop

Use this when the user wants project advancement to be managed explicitly through Linear and Slack, not just code changes.

## When to use
- The repo is `metaverse-office-web`.
- The user expects each slice to be tracked in Linear and announced in Slack.
- You are shipping a small read-only or operator-surface slice through a repo-local worktree.

## Core rule
Code delivery is only one part of the loop. The full loop is:
1. inspect main
2. choose next smallest slice
3. create/update Linear issue
4. announce start in Slack
5. create repo-local worktree
6. implement with Codex
7. run gates
8. run Codex review
9. push branch + open PR
10. squash merge
11. fast-forward local master and clean up worktree/branch
12. mark Linear done
13. announce completion in Slack
14. seed the next Linear slice

## Minimal operating procedure

### 1. Inspect main first
- Confirm `master` is clean
- Confirm latest merged commit
- Confirm no stale worktrees are hanging around

Example:
```bash
git status --short --branch
git log --oneline -5
git worktree list
```

### 2. Pick the next smallest real slice
Prefer:
- read-only drilldown tightening
- pivot dead-end removal
- regression-proof additions for already-exposed UI semantics

Avoid:
- new domains
- widened request surfaces
- write paths
- broad cleanup disguised as progress

### 3. Create the Linear issue before coding
- Create one issue per slice
- Put it directly into `In Progress` if you are starting immediately
- If you are only seeding the next slice and not starting implementation yet, leave it in `Todo`
- Keep the body concrete: current context, exact scope, acceptance, and non-goals

Implementation note:
- If terminal `curl`/shell quoting starts fighting GraphQL payloads, prefer `execute_code` with Python `urllib` to load `~/.hermes/.env`, call Linear GraphQL, and print structured JSON. It is more reliable than nested shell quoting for issue lookup/create/update.
- On this MYC team, `issueCreate` may default a new issue to `Backlog` instead of `Todo`. If you are seeding the next slice, explicitly set the issue state to the team `Todo` state after creation; if you are starting immediately, explicitly move it to `In Progress`.
- Stronger state-selection rule from MYC-42: do not pick workflow states only by `type`. This team can expose more than one `started` state (for example both `In Progress` and `In Review`). When starting a slice, prefer the state named exactly `In Progress`; when closing a slice, prefer the completed state named exactly `Done`; only fall back to `type` matching if the named state does not exist.

Good issue body sections:
- Context
- Scope
- Non-goals
- Acceptance

### 4. Announce start in Slack
Post to `#metaverse-office`:
- Linear issue id + URL
- one-line scope
- explicit statement that this is read-only and request-surface constrained if relevant

### 5. Create a repo-local worktree
Example:
```bash
mkdir -p .worktrees
git worktree add -b slice/<issue-slug> .worktrees/<issue-slug> origin/master
```

### 6. Fix worktree dependencies if needed
In a fresh worktree, if `node_modules` is missing:
- resolve worktree git dir with `git rev-parse --git-dir`
- run `mkdir -p "$gitdir/info" && touch "$gitdir/info/exclude"` before editing excludes; some repo-local worktrees do not create the `info/` directory yet
- add `node_modules` and `apps/web/node_modules` to `<gitdir>/info/exclude`
- symlink both paths back to the main workspace
- for this repo-local layout, from the worktree root the correct symlinks are:
  - `node_modules -> ../../node_modules`
  - `apps/web/node_modules -> ../../../../apps/web/node_modules`
- verify `apps/web/node_modules/.bin/vitest` exists before continuing

### 7. Implement with Codex
- Always `unset OPENAI_BASE_URL`
- Give Codex a surgical prompt
- Tell it not to commit
- Tell it to run only the smallest relevant tests first

### 8. Validate in layers
- Layer A: smallest targeted proof first
- Review before expensive gates
- Current repo full gate only when candidate-ready
- Async/nightly full regression belongs to Layer C
- Details: `references/workflow-optimization-addendum-2026-04.md`

### 9. Run explicit Codex review
Use a separate Codex review pass against the current diff.
Do not merge without explicit `Verdict: APPROVE`.

Important interpretation rule:
- `REQUEST_CHANGES` is not a hard-stop on the whole vision; it means iterate inside the slice until the slice is correct.

### 10. Push, PR, squash merge
- Commit with a narrow conventional message
- Push branch
- Open PR against `master`
- PR title must use Conventional Commits style (`feat(scope): ...`, `fix(scope): ...`, etc.). Do **not** start PR titles with the Linear id like `MYC-123 ...`.
- Keep the Linear id in the PR body, branch name, Slack, and Linear trail instead.
- Include validation summary and Linear issue id in the PR body
- If the PR is owned by the same GitHub identity you are using for automation, do not try to self-approve: GitHub rejects `APPROVE` reviews on your own PRs. In that case, leave a `COMMENT` review summarizing the independent Codex review result and keep the actual approval fact in the PR body / Linear / Slack trail.
- Squash merge when green and approved
- Squash merge commit title must also use Conventional Commits style, not a Linear-id prefix. Example: `feat(world): preserve viewport clamp padding inspector sync (#136)`

### 11. Fast-forward and clean up immediately
From the main repo:
```bash
git checkout master
git pull --ff-only origin master
git worktree remove .worktrees/<issue-slug>
git branch -D slice/<issue-slug>
git push origin --delete slice/<issue-slug>
```

Why `-D` here:
- this conveyor squash-merges PRs
- after a squash merge, the slice branch tip usually is **not** an ancestor of `master`, even though the content is already landed
- `git branch -d` will therefore warn that the branch is "not fully merged" and can slow or confuse cleanup
- only use `-D` **after** you have verified the PR is merged and local `master` has been fast-forwarded to the merged commit

### 12. Close the project-management loop
After merge:
- move the Linear issue to `Done`
- post completion message in Slack with PR URL, summary, and validation result
- create the next Linear issue while context is fresh

## Slack delivery fallback
Do not rely blindly on Hermes target discovery.

Observed real-world failure:
- `send_message(action='list')` may omit Slack targets in the current session
- `send_message(target='slack:#metaverse-office')` can fail even when Slack is healthy

Observed working shortcut on this machine:
- even when channel-specific Slack resolution fails, bare `send_message(target='slack', ...)` still delivers to the configured Slack home channel
- if the project channel is the Slack home channel (for this user it is `#metaverse-office` / `SLACK_HOME_CHANNEL`), prefer that bare-target send first before dropping to direct API calls
- Hermes Slack sends can also fail transiently with `Server disconnected`; treat that as a retryable transport flake, not as proof that Slack auth/channel resolution is broken. Retry the same bare `send_message(target='slack', ...)` once before escalating to API-level diagnosis.

If that still fails, verify Slack functionally with direct API calls:
- `auth.test`
- `conversations.list` or `conversations.info`
- `chat.postMessage`

If those succeed, post directly using the Slack API and treat Hermes target discovery as stale session state, not an integration failure.

- Stronger multi-PR closeout rule learned from MYC-87/88/89: when several sibling PRs target the same `master`, merging the first one can leave the next siblings in a short recomputation window where GraphQL `mergeable` / `mergeStateStatus` shows `UNKNOWN` or REST `pulls/{n}.mergeable` is `null`, even though the head commit `statusCheckRollup.state` is already `SUCCESS` and the merge API will succeed. In that state, do not misclassify the PR as blocked. Re-read `pulls/{n}` a few times with a short bounded retry to let GitHub compute mergeability; treat a transient `UNKNOWN` as recomputing state, not as a red gate. Keep REST `combined_status` out of the decision path here.

Query `/commits/{sha}/check-runs` to confirm the duplicate run situation, then query `/check-runs/{id}/annotations` or `/actions/jobs/{job_id}` to identify the exact failing step/test when log download is unavailable or 401s. If the failure looks like a transient CI flake on an otherwise locally green SHA, rerun only the failed job with `POST /repos/{owner}/{repo}/actions/jobs/{job_id}/rerun` instead of re-pushing code. Report the slice as still blocked until the rerun turns green; do not merge on the strength of the successful sibling run alone.

Rebase the local sibling worktree onto the new `master`, rerun validations on the rebased local SHA, and force-push the rebased branch before waiting on GitHub again. Do **not** keep polling the old remote SHA after a local rebase; the correct next step is to publish the new head and then wait on refreshed checks for that new SHA.

Transient TLS/transport faults like `URLError: [SSL: UNEXPECTED_EOF_WHILE_READING]` can kill an otherwise-correct sequential closeout mid-run. If a background closeout process dies on one of these transient network errors, fix the helper with retries and relaunch it; do not misclassify that as a product/CI regression.

In closeout automation, do not stop on that SSH flake. Before timing out, inspect the live job steps (`actions/jobs/{job_id}`) and prefer a much longer bounded wait when the final step is still making forward progress. A helper timing out in that state is an automation-budget issue, not proof the PR is blocked.

First inspect the live job-step state and wait for the in-progress sibling to settle; only after both duplicate jobs finish should you decide whether this is a real red or a duplicate-run flake worth rerunning.

## Pitfalls
- Don’t create a PR-sized code change before the Linear issue exists. The tracking object should predate implementation.
- Don’t stop at “PR merged”; mark the Linear issue done and post Slack closure, or the management loop is incomplete.
- Don’t assume current Slack target discovery is authoritative.
- New closeout pitfall from MYC-109: a test-only slice can pass its targeted Vitest or browser-smoke command and still fail `tsc`/full gate because inline fixture objects widen literal types (`'yellow'` -> `string`, etc.). Do not merge test-only PRs on the strength of the targeted command alone; run at least `pnpm --filter @metaverse-office/web typecheck`, and prefer the normal full gate.
- Don’t skip next-issue seeding after merge; you will lose momentum and context.
- In resumed cron/conveyor runs, re-resolve the repo realpath, `git fetch origin --prune`, inspect `git worktree list`, and check recent `master` commits before touching any previously-known slice worktree paths. Another autonomous pass may already have merged the PR, fast-forwarded `master`, and removed the repo-local worktree/branch. Treat a missing `.worktrees/<slice>` path as a signal to audit `master`/PR/Linear state first, not as proof of failure.
- Stronger resumed-run rule learned from MYC-65/67/68: if the remembered background Codex `process` IDs come back `not_found`, do not assume the slice stalled. First audit `master`, open/closed PRs, Linear state, and recent Slack delivery for that slice. In this conveyor, another autonomous pass may have finished the review/merge/cleanup path and invalidated both the old worktree path and the old process handle.
- Companion rule: if the slice commit is already on `master` and the slice branch/worktree are gone, do not recreate or replay the old worktree. Close the remaining management loop only: verify master is clean, verify the full gate on master if still needed, mark Linear done if not already, and send the Slack merge signal.
- Stronger concurrent-conveyor rule learned from MYC-70/71: the same disappearance can happen *mid-run*, not only on a resumed cron. If a previously-live repo-local worktree path suddenly stops existing after you finish a gate/review step, treat that as a state-change signal, not as filesystem corruption. Immediately audit `master`, recent PRs for the slice branch, remote branch existence, `git worktree list`, Linear state, and recent Slack delivery. Another autonomous pass may already have pushed, opened the PR, squash-merged it, fast-forwarded `master`, and removed the worktree/branch while your current run was still active.
- In that mid-run disappearance case, do not recreate the worktree just to continue the old local plan. First verify whether the rebased slice commit SHA already appears as the PR head or whether the squash merge already landed on `master`. If yes, switch from implementation mode to management-closeout mode: backfill any missing Linear state transitions (`In Review`/`Done`), send any missing Slack PR-ready / merge messages with an explicit audit/backfill note, confirm `master` is clean, and report the real merged SHA rather than the now-gone worktree SHA.
- Stronger validation rule learned from MYC-74/75: if a long `pnpm test:all` run starts printing parser/build errors from a slice worktree and that worktree later disappears or its HEAD changes mid-run, do not assume the slice itself is still broken. Another conveyor pass may have amended the commit, rerun gates, merged the PR, and removed the worktree while your old gate process was still streaming stale output. Re-audit `git worktree list`, current `master`, PR state, and remaining worktree HEADs before spending time debugging the old log.
- Accessibility follow-up learned from MYC-74: when a collector workspace preview (or similar provenance preview) changes from plain text into a shared-memory jump button, keep the freshness/timestamp copy in the accessible name as well as the visible label. Otherwise the focused component test may stay green while independent review correctly flags that the button no longer exposes the same preview context to assistive tech. Add assertions for the full aria-label, not just button text.
- Stronger handoff rule learned from MYC-69/70/71: when one slice in the batch is fully merged but sibling slices are only partially advanced, schedule a one-shot resume cron immediately instead of ending the session with implicit local state. Put the exact per-slice handoff facts into the cron prompt: branch/worktree path, whether the branch is already committed or still dirty, whether it is ahead/behind master, whether full `pnpm test:all` already passed after the latest rebase, whether independent review already reached APPROVE, and which delivery-chain steps remain (push/PR/Linear/Slack/merge/cleanup vs commit/rebase/revalidate/re-review first). This avoids resumed runs wasting time rediscovering which slices were implementation-complete versus delivery-complete.
- In that same mixed-state handoff, say explicitly whether the cron is continuing the remaining delivery chain or only doing final cleanup. Do not leave the future run to infer that from vague wording like "finish the batch".
