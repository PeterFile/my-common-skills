# Parallel worktree + Codex review loop

> Archive note: this is a superseded source workflow kept for provenance and rare edge cases. Do not use it as the primary operating path. Start from `../SKILL.md` and `references/legacy-index.md`; migrate any still-valid compact rule into the current skill before relying on this archive repeatedly.

Use this when the user wants breadth-first delivery, stacked repo-local worktrees, and multiple Codex agents in parallel instead of one-worktree serial execution.

## When to use
- Repo must move faster through breadth-first slices.
- 2-3 thin slices can be isolated with low file-overlap risk.
- Codex is available and should do implementation work.
- Validation green alone is not enough; each slice still needs an explicit review pass.

## Core rules
1. Create repo-local worktrees under `.worktrees/`.
2. Launch multiple Codex agents in parallel only for low-overlap slices.
3. Do not regress into one-worktree serial waiting. Maintain a conveyor belt: one slice implementing, one slice under validation/review, and one slice being rebased/pushed/opened as a PR whenever backlog permits.
4. Treat first-pass Codex output as provisional even when tests are green.
5. Always run an independent review pass after implementation.
6. If review returns REQUEST_CHANGES, fix in place, revalidate, and re-review before push/PR.
7. Do not claim PR-ready status until validation AND review are both green.

## Slice selection heuristic
Pick 2-3 slices from different layers, for example:
- world/runtime visibility slice
- read-only API/contract slice
- operator/accountability/details-panel slice

## Optional Graphite upgrade for stacked development
When the repo/user wants stacked PRs and the parallel worktree count is starting to explode, do not keep scaling by "one tiny slice = one worktree" forever. Prefer this split of responsibilities:
- worktree = theme/workgroup boundary (for example world-runtime, supervision-accountability, ops-replay)
- Graphite stack = ordered stacked PRs inside that one theme worktree
- Linear = lifecycle state (`Todo`, `In Progress`, `In Review`, `Blocked`, `Done`)
- Slack = notifications only, never the state source
- local controller file = minimal execution metadata only (`active_process`, `health`, `next_action`)

Important simplification rule: keep lifecycle state tiny and external, keep execution health local and diagnostic. Do not invent a giant custom state machine. Treat values like `running`, `waiting`, `stalled`, `no-op`, `degraded`, and `baseline-red` as local health flags, not as project-management states.

Practical consequence:
- parallelize across a small number of theme worktrees
- stack sequential dependent slices within each theme using Graphite (`gt create`, `gt submit --stack`, `gt modify -a`, `gt sync`, `gt restack`)
- let the main agent orchestrate workgroups and next actions instead of micromanaging dozens of tiny independent worktrees

Graphite environment findings from April 2026 on this machine:
- install works via `brew install withgraphite/tap/graphite`
- non-interactive repo init works with `gt init --trunk master` (or the actual trunk branch)
- do not assume auth lives at `~/.graphite_user_config`; on this machine the auth token is stored under the XDG path `~/.config/graphite/auth`
- before declaring Graphite auth missing, check both the repo config (`.git/.graphite_repo_config`) and the XDG auth path
- even when the auth file exists, treat GitHub-side readiness as unverified until one real `gt submit` / `gt submit --stack` succeeds in the target repo

Use breadth-first planning on purpose. Each batch should touch multiple parts of the real vision instead of tunneling vertically through one local area for several PRs in a row.

A reliable `metaverse-office-web` batch template is:
- one world layer / runtime visibility slice
- one supervision / evidence / shared-memory / accountability slice
- one backend runtime contract or operations / workflow / replay slice

If the current Linear queue is empty or stale, do not stall on planning. Seed the next 3 issues yourself immediately, one per lane, and move them straight to `In Progress` so implementation can start in parallel.

Graphite workgroup bootstrap follow-up from April 2026: when migrating this repo from legacy `1 slice = 1 worktree` into theme workgroups, do not invent a giant local PM state machine and do not start by rewriting every active lane. First run a live preflight in the real repo (`git status --short --branch`, `git worktree list --porcelain`, versions for `git/gt/node/pnpm/codex`, open PR inventory, Hermes `process list`, and a real `unset OPENAI_BASE_URL && codex exec 'Reply with exactly OK...'` probe). Then read the repo-local operating-model plans before acting. Create only the minimum local controller artifacts under `.hermes/orchestrator/`: a `workgroups.json` with `worktree/theme/linear_cycle_state/graphite_stack/active_branch/active_process/health/next_action`, plus a compact handoff markdown. Keep lifecycle truth in Linear, notifications in Slack, code dependency truth in Graphite/GitHub, and execution truth local.

For the first Graphite pilot, pick one genuinely cold theme and prove the conveyor with a real next action, not another planning pass. A good bootstrap pattern is: inventory open lanes / stale lanes / hot files / candidate cold themes, choose the cold pilot, launch the exact validation in background with `notify_on_complete`, immediately record the `session_id` and successor action in `workgroups.json`, then poll and classify before doing anything else.

Important rescue rule learned from PR #264 bootstrap: if a cold pilot worktree is dirty and its validation fails, do not jump straight to push/review and do not assume baseline-red. Reproduce the exact failing command on the dirty lane, rerun the same exact selector on clean `master`, and classify from that comparison first. In the observed incident-contracts lane, the dirty worktree failed a single backend smoke with `500 != 200` while `master` passed the same selector, proving a slice regression. The root cause was a partially landed helper call (`getOpenLifecycleIncidentTieRank(...)`) with the helper body missing, so the right move was the smallest surgical repair, rerun the exact selector, then rerun the full lane validation and only then amend/review/push. This pattern is reusable for any dirty-lane salvage during workgroup migration.

Stronger follow-up learned from the MYC-126 -> MYC-142/143/144 handoff: do not blindly resume the oldest existing Todo issues just because they already exist in Linear. A Todo queue can contain stale or already-covered ideas while mainline has moved on. Before choosing the next batch, inspect current master code/tests and compare them against the queued issue intent. If a queued Todo is already covered by landed tests/behavior, treat it as stale/duplicate and seed a fresher adjacent slice instead of wasting a worktree on redundant work.

Avoid parallel slices that all touch the same hot files unless they are explicitly provisional and will be reconciled later.

A practical exception: two read-only UI enrichment slices may still run in parallel against the same large component when each slice is fenced to a different sub-renderer or semantic card (for example one branch only touches workflow peer-watch alert cards while another only touches interaction cards in the same DetailsPanel). In that case:
- state the no-touch subareas explicitly in each Codex prompt
- expect the later branch to be rebased after the earlier one lands
- rerun the full repository gate after the rebase, not just the focused component test

Stronger batch-conveyor follow-up from MYC-142/143/144: even when 3 thin slices all touch the same hot smoke file (for example `apps/web/e2e/operator-shell.keyboard.smoke.spec.ts`), it can still be correct to implement and validate them in parallel **if** each slice stays narrowly scoped, has its own targeted validation, and you treat the PRs as provisional siblings rather than merge-ready in arbitrary order. In that pattern:
- allow the parallel implementation/review/push/PR-open phase to keep throughput high
- mark each slice only as `PR-open / In Review`, not delivery-complete
- post Slack/Linear notes that the batch shares a hot file and requires sequential closeout
- after opening each PR, check the live GitHub head SHA and combined status immediately; if the PR still shows `state: pending` with `total_count: 0`, treat it as `PR-open / waiting-for-remote-signal` rather than merge-ready
- stronger remote-check rule from PR #264: do not conclude "no checks exist" from the MCP aggregate alone. If `mcp_github_get_pull_request_status` still shows `pending / total_count: 0`, cross-check the live GitHub PR Checks/Actions page in the browser. Browser truth can reveal a more specific split state such as `push` still running while `pull_request` is already failed. Drive the next action from that more specific run-level truth, not from the stale aggregate.
- after the first sibling merges, fast-forward `master`, then rebase each remaining sibling in sequence onto the new `master`
- rerun at least the normal required validations on each rebased sibling before merging it
- schedule a closeout continuation cron immediately if you cannot stay online long enough to finish that sequential rebase/merge path in the same session; include PR numbers, expected Linear states, and the required merge/ff/cleanup sequence so the conveyor can resume truthfully
## Setup steps
1. Confirm main/master is clean.
2. Preflight the operating lane before coding:
   - current worktrees
   - open PR count
   - background agent/process count
   - Codex availability
   - Node/pnpm availability

   For Codex availability, do not rely on stale memory about a past auth outage. Probe it live in the target repo after `unset OPENAI_BASE_URL`:
   - `codex --version`
   - `codex exec 'Reply with exactly OK and exit. Do not inspect, change, or create any files.'`
   - `codex review --base origin/master`

   Interpret the result correctly:
   - if `exec` returns `OK` and `review` completes, Codex is usable for the batch even if optional MCP/Vercel startup noise appears
   - treat lines like `AuthRequired ... invalid_token`, `rmcp::transport::worker ... Transport channel closed`, or Vercel MCP login warnings as non-blocking unless they actually stop local repo work
   - only mark Codex degraded when the live probe itself fails to complete or cannot perform the requested local repo action
3. If the next batch is not already obvious, do a fast three-lane reconnaissance before seeding work:
   - inspect the actual current code/tests, not just old plans
   - derive one smallest adjacent slice for world/runtime/viewport
   - derive one smallest adjacent slice for supervision/evidence/shared-memory/accountability
   - derive one smallest adjacent slice for operations/workflow/correlation/replay
   - prefer already-loaded fields and already-existing contracts over new surfaces
   - best practice for Hermes: spawn 3 parallel subagents, one per lane, and require each to return a concrete Linear-ready slice with title, exact scope, non-goals, acceptance, likely touched files, and why it is the smallest correct next step
   - then seed all 3 Linear issues immediately, move them to `In Progress`, send one Slack batch-start message, create all repo-local worktrees, and only then launch Codex in parallel
4. Create worktrees under `.worktrees/`.
5. In pnpm monorepos, verify fresh worktrees can resolve shared dependencies before running validation.
6. If dependency resolution fails in a fresh worktree, reuse the repository's existing dependency installs instead of reinstalling everything.
7. Verify the expected package binary exists before running validation.
8. Launch all chosen Codex slices before waiting on any single one; the whole point is to avoid one-worktree serial idle time.
9. In a chat-bound session, if you start background Codex agents and then need the conveyor to continue after this turn ends, schedule an external wake-up immediately (for example a one-shot cron job with a self-contained resume prompt). Background Codex alone is not enough; without wake-up the conveyor stalls when the current turn ends.
10. Before seeding the next batch, audit whether the currently-active Linear `In Review` slices are already merged on GitHub and fast-forwarded into local `master`. If they are, mark them `Done` first so the next-batch queue is not contaminated by stale already-finished work.
11. If the recent mainline stream has drifted into test-only or hardening-heavy commits and the user explicitly wants faster feature delivery, do not keep extending that lane by inertia. Re-inspect current master, derive three feature-first slices from the real shipped code, and seed those immediately even if the easiest available work would be more tests.
12. If Slack/chat delivery is unavailable in the current environment, do not stall the conveyor waiting for comms. Keep Linear as the source of planning truth, note that Slack sync is degraded/unavailable, and continue the worktree/Codex/PR loop honestly.
13. Concrete Slack degradation rule from April 2026: if direct Slack API validation returns `invalid_auth` and Hermes target discovery shows no Slack targets, classify Slack as degraded for the batch immediately. Do not keep retrying target discovery as if delivery were merely delayed, and do not claim any Slack sync happened. Record the degraded state in Linear / final status and keep the conveyor moving with GitHub + Linear as the truthful control plane.
14. GitHub MCP fallback rule from the same closeout: when `gh auth status` is unavailable or `gh` is missing but `mcporter` can reach the GitHub MCP server, use `mcporter` for PR inventory, check-run inspection, comments, and merge/closeout instead of stalling. Important syntax finding: for methods like `pull_request_read`, prefer function-style calls such as `github.pull_request_read(method: "get_check_runs", owner: "PeterFile", repo: "metaverse-office-web", pullNumber: 259)`; the loose `key=value` form can silently misparse required numeric args like `pullNumber`. Likewise, `merge_pull_request(...)` can be used for final merge once local validation + independent review are green.

## Main-agent controller loop and continuation hygiene

Treat the main Hermes session as the control plane and every worktree lane as explicit state, not as implicit chat memory.

### Required control artifacts
- Keep one repo-local controller file under `.hermes/orchestrator/` (for example `lanes.md`, `lanes.json`, or `checklist.md`).
- For each lane, record at minimum:
  - Linear issue / slice name
  - worktree path
  - branch
  - owner agent (`codex`, `hermes-subagent`, manual)
  - lane state (`seeded`, `implementing`, `validating`, `review`, `pr-open`, `waiting-remote`, `merged`, `blocked`, `no-op`, `stalled`)
  - current background `session_id` if any
  - exact next action
  - exact validation command / review command
  - latest truth source (commit SHA, PR number, failing test, or blocker)

### Background-command rule
- Any long command (Codex implementation, browser-smoke, full gate, review) should run in background with `notify_on_complete=true`.
- But `notify_on_complete` is only a signal, not the scheduler. The real source of continuity is the controller file plus an external wake-up path.
- Immediately after launching a background process, write its `session_id`, start time, expected success condition, and exact successor step into the controller file before doing anything else.

### Wake-up rule
- In a chat-bound session, do not assume the current turn will still exist when the process finishes.
- If the conveyor must continue without waiting for the user to manually ping, create the wake-up path from the interactive controller session right away (for example one recurring or one-shot cron that reads the controller file and resumes the next exact step).
- Do not make cron-run sessions recursively schedule more cron jobs. Prefer one stable controller cron created from the interactive session, or recreate the next wake-up only from an interactive parent session.
- If tool-call/session budget is already low, do **not** launch another background Codex slice or long browser-smoke just to preserve momentum. First write the controller/handoff with PR numbers, head SHAs, background session ids, exact running commands, and the implementation-vs-delivery distinction; then create/verify the wake-up path. Only start the next slice when continuation is actually recoverable from repo/GitHub/controller truth.
- If a hard stop interrupts after a PR is opened but before CI/merge/cleanup finishes, the next session must begin in closeout/audit mode: poll current PR head checks, poll or classify any recorded background processes, verify on-disk worktree state, and only then decide whether to merge, rebase, or continue stacked work. Never infer delivery-complete from a local green gate plus an open PR.

### On every wake-up / next round
1. Poll the referenced background process first.
2. If the recorded `session_id` returns `not_found` in a cron/fresh continuation, do **not** infer success or failure from the missing process. Treat the controller process id as stale runner-local bookkeeping, then audit on-disk/GitHub truth: current worktree HEAD, remote branch SHA, existing PR/head SHA, PR comments/body, and local validation evidence. If the required validation result is not independently recoverable, rerun the exact gate in the target worktree and record the new `session_id` before advancing.
3. Audit on-disk truth: `git status -sb`, current HEAD, worktree diff, relevant test result, PR head SHA if applicable.
4. Update the controller checklist/state file.
5. Choose exactly one next precise action per lane (revalidate, review, push, rebase, fix review finding, open PR, merge, cleanup, or mark blocked/no-op).
6. Launch that action immediately or mark why it cannot run.

### 60/60 fresh-continuation rule
- Do not stretch one conversation forever.
- When the session is nearing the practical context/turn limit (the user's shorthand: `60/60`), stop launching new work from that thread.
- First write a compact handoff summary under the repo-local `.hermes/orchestrator/` area with:
  - current lane table
  - active/background session ids
  - strongest fresh evidence per lane
  - exact next command for each live lane
  - what is intentionally not yet done
- Then resume in a fresh continuation session that reads only the controller file + latest handoff summary, instead of depending on a huge prior transcript.

This keeps the conveyor breadth-first, auditable, and restartable.

## Execution loop per slice
1. Give Codex a narrow prompt with:
   - exact scope
   - hard no-touch files when needed
   - required validations
   - commit message
   - instruction not to push
2. Wait for Codex to finish.
3. Check branch state and commit state manually.
4. Run the required validations yourself if needed.
5. Run a separate Codex review against `master...HEAD` (or `main...HEAD`).
6. If review says REQUEST_CHANGES:
   - feed the exact review findings back into Codex
   - keep the fix surgical
   - prefer amend/rewrite of the existing slice commit when practical
   - rerun validations
   - rerun review
7. Only after APPROVE + green validation:
   - push
   - open PR

## Review checklist
Independent review must explicitly check:
- correctness
- regressions
- accessibility/semantics for UI changes
- contract fidelity for API changes
- test adequacy
- unnecessary complexity

## Important experiential findings
- Codex implementation often reaches green tests before semantic correctness is actually right. Review must stay independent.
- Validation can miss real issues like stale-state semantics, misleading labels, or request-surface widening.
- Important operator reality: even if your prompt says "do not commit / do not push / do not open a PR", Codex may still create commits, push the branch, or open the PR. Always inspect local branch state, remote branch state, and open PRs immediately after Codex exits. If Codex pre-opened the PR, treat it as provisional only: rerun your own validation, rerun independent review, and only then signal PR-ready / In Review.
- Stronger PR-readiness audit learned from the MYC-174/175/176 batch: after a local slice is already committed, pushed, and even opened as a PR, do **not** assume the PR head stays current just because the branch name matches. A local worktree can advance again afterward, leaving `git status -sb` as `ahead 1, behind 1` against the remote PR branch while GitHub is still evaluating the older head SHA. Before waiting on CI or declaring a slice truly PR-ready, compare three SHAs explicitly: local worktree `HEAD`, remote branch SHA, and `pulls/{n}.head.sha`. If local `HEAD` has moved and that new local head is the intended truth, rerun the required local validations on that refreshed head, force-push the same branch, and update the PR/Linear/Slack trail to say the earlier PR head CI is obsolete and the refreshed head SHA is now the source of truth.
- Additional remote-tracking gotcha from the MYC-203 replay-severity lane: immediately after force-pushing or rewriting a slice branch, the local worktree can transiently report `ahead 1, behind 1` against `origin/<branch>` even though the remote branch and GitHub PR head already point at the new local commit. Before classifying that as real divergence, check the live PR head SHA and the remote branch SHA directly, then refresh the local remote-tracking ref with `git fetch origin <branch>`. If PR head + remote branch already match local `HEAD`, treat the stale `ahead/behind` output as a local tracking lag, not as proof that another force-push or salvage commit is needed.
- Closeout follow-up from the April 2026 5-lane batch: when PR creation returns GitHub validation `A pull request already exists for <owner>:<branch>`, do not treat that as a fresh failure and do not open a duplicate branch. List PRs by `head=<owner>:<branch>` (or otherwise query the existing PR for that exact branch), confirm the current PR number/head SHA, and continue by updating that existing PR's review trail/comments with the new validation/review evidence. Also re-check `origin/<branch>` vs local `HEAD`; if they already match, the lane is PR-open and waiting on remote signal, not blocked.
- Validation-trail correction follow-up from the MYC-210/211 continuation: if an existing PR body or earlier audit comment contains a provisional blocker note that later reruns disprove on the current intended head (for example an old "baseline-red" caveat), do not leave that stale note standing as latest truth. Post an explicit corrective PR/Linear comment with the new head SHA, exact rerun command, and green result, and treat that newest rerun as the source of truth.
- New follow-up from the April 2026 5-lane resume batch: even after a Codex run exits 0, creates a commit, and you open the PR, do **not** trust the worktree state you saw a few minutes earlier. Re-check `git status -sb` immediately before final PR-ready reporting and again after any later validation/review step that touched the same worktree. A slice can still have uncommitted local drift in tracked files (for example the worktree file content no longer matches `HEAD`, or a later local fix leaves the branch `ahead 1, behind 1` versus `origin/<branch>`). If that happens, the stronger source of truth is the current on-disk worktree plus a fresh rerun of the targeted validation, not the older green run or the already-open PR. Salvage the dirty state, review the effective current diff, recommit/amend as needed, rerun the targeted validation, and `git push --force-with-lease` before you call the lane implemented/validated/PR-open.
- Another Codex transcript pitfall from the same conveyor: the terminal transcript itself can wander into irrelevant memory/search/rollout chatter or other non-repo noise even when the process exits. Do not treat raw Codex stdout as proof that a slice changed the right file or ran the right gate. Source of truth stays on-disk repo state plus your own rerun of the validation command.
- For UI overlay additions, check viewport/clamp behavior; new overlays may require padding changes on more than one edge.
- World-shell overlay follow-up from MYC-157: if you convert `.aitown-panel__topline > span` into flex/card chrome while mobile media queries switch the parent topline to `flex-direction: column`, remember that flex items default to `align-self: stretch`. In this repo that can silently turn each topline card into a full-width clamp contributor on portrait, inflate top/right clamp padding, and break fresh-load drag reachability or selected-watch portrait smokes. Keep those cards opt-out of stretch (for example `align-self: flex-start`) and rerun the portrait viewport/browser-smoke canaries before calling the slice green.
- For accessibility descriptions, do not attach dynamic or misleading legend text to a region unless the described text is always true.
- Topline/action-chip accessibility follow-up from MYC-210: when adding new shell/topline focus chips or similar read-only summary buttons, do not give them an action-only `aria-label` that overrides the visible severity/occupant summary text. In this repo that silently hides the important context from screen readers even though sighted users still see it. Safe pattern: include the same visible summary tokens in the accessible name (for example `Zone · Orange severity · 1 agent · Focus in world viewport`) and update App/browser tests to assert the richer accessible name instead of the shorter action-only label.
- Queue/filter follow-up learned from MYC-195: when a slice adds a new backend filter or query param (for example `severity` on `/office/operations`), do not stop at backend route/store wiring plus API-helper forwarding. Before approval, audit the shipped operator path end-to-end: the App resource state, request keying, DetailsPanel control surface, and focused App/DetailsPanel tests must expose the new filter so the user can actually drive the contract from the shell. A green backend smoke plus green `api.ts` helper test is not enough if the UI still only exposes the old state filter.
- Audit-source truncation follow-up from the accountability interaction-provenance slice: if a panel aggregates `Source` kinds into a deduped fixed-width list (for example `.slice(0, 5)`) while `What` is chosen from a prioritized list of evidence summaries, do not append a new provenance kind after the old sources and assume it will stay visible. In this repo that let interaction provenance disappear from the rendered `Source` line whenever alerts/incidents/handoffs/timeline sources filled the first five slots, even though `What` came from an interaction. Safe pattern: when `What` is driven by a specific record type, promote that record type's provenance to the front of the aggregated source list before truncation, and add a crowded-source regression proving the matching provenance still renders when multiple older source kinds are present.
- Selected-agent active-correlation queue follow-up learned from MYC-188: do not complete a crew-overview lane by only duplicating its `DetailsPanel` rendering into selected-agent mode. In this repo `operationsResource` is intentionally disabled on agent-only paths unless a selected-operation request is active, and `usePolledResource` clears disabled resources back to idle with no data. If you simply render the same lane whenever `selectedCorrelationId` is active, selected-agent preserved-correlation pivots can show a blank `Active Correlation Queue` section with only the heading/scope and no rows or status copy. Correct fix: either (a) cache/reuse the last crew-overview full operations snapshot in `App` and pass that dedicated snapshot/state/error into the selected-agent lane, or (b) suppress/render explicit unavailable copy for the idle/no-snapshot state. Required regression coverage: an App-level test for the selected-agent preserved-correlation path that does NOT select the current-operation request, proving the lane is either truthfully populated from cached crew-overview data or truthfully absent/unavailable — never a blank section.
- Hot-zone summary follow-up learned from MYC-196: when a world/runtime legend summarizes a collapsed boolean signal such as `has_open_incidents`, re-check what that boolean really means upstream before writing user-facing copy. In this repo the projector boolean can combine peer-watch alerts and workflow incidents, so copy like `open incidents` or `occupants with open incidents` can be false even if tests are green. Either compute the narrower metric for real, or rename the summary field/copy/tests to the truthful combined meaning (for example `open alerts or incidents`).
- Incident-feed runtime-risk follow-up from the world-incident-feed lane: if you backfill `WorldAgent.open_alert_count` / `has_open_incidents` from `/incidents` when workflow coverage is missing, do **not** count raw feed rows as if each active-looking row were still current. That feed is historical and can contain an older `open` / `waiting` row plus a newer `resolved` / `completed` row for the same lifecycle. Correct pattern: collapse feed incidents to the latest row per lifecycle key only for lifecycle-based incident kinds, and do not include `actor_id` for handoff/reboot because start/complete may be performed by different valid actors. Prefer a contract-provided lifecycle identity when available; otherwise use stable lifecycle fields such as agent + kind + correlation + sorted counterparties. Keep peer-watch alerts distinct by stable alert identity (`incident_id` / resolved-alert metadata where available) instead of collapsing them by correlation tuple, because multiple same-tuple alerts can be open concurrently and resolve independently. Companion rule: keep `open_alert_count` semantically narrow — in this repo it feeds UI text/legend that explicitly means peer-watch alert count, so only active `peer_watch_alert` rows should backfill that field; broader active handoff/reboot state may drive `has_open_incidents` but must not inflate the alert counter. Required regression coverage: (1) active peer-watch + active handoff with no workflow coverage yields `open_alert_count === 1` and `has_open_incidents === true`; (2) an older active row followed by a newer resolved/completed row for the same lifecycle yields `open_alert_count === 0` / `has_open_incidents === false`; (3) workflow-present agents remain workflow-authoritative and do not inherit feed counts.
- World/runtime projector follow-up from the incident-feed backfill lane: before reusing a broader incident-feed signal to populate an existing field, audit every downstream consumer of that field, not just projector tests. In this repo `open_alert_count` is already semantically narrower than `has_open_incidents`: downstream consumers include the scene badge legend (`Peer-watch alert count`), `selectAgentLabel(... "alert(s)")`, and the DetailsPanel `Alerts` row. If you backfill `open_alert_count` from all active incidents (handoff/reboot/peer-watch) just because the type is `number`, tests can go green while the UI lies. Safe pattern: keep the narrow counter narrow (for example peer-watch alerts only), use a separate broader signal for combined incident truth (`has_open_incidents`), and expand the focused validation set to include any selector/legend tests that encode the field semantics, not only projector/unit tests.
- Stronger incident-feed projector follow-up from the April 2026 closeout audit: a full local `pnpm web:test:browser-smoke:dev` pass is still weaker than an independent semantic review for world/projector slices. In the observed lane, the branch passed full dev smoke while the projector diff still had two real gaps: feed-only active incidents raised `open_alert_count` / `has_open_incidents` but did not raise agent/world/watch-edge severity, and feed-only handoff/reboot statuses were not threaded into `extractPhaseSignals`, so phase/zone stayed on raw state instead of `handoff_*` / `reboot-zone` semantics. Safe rule: for feed-backfill slices, review the projector against all downstream contracts — agent severity, `summary.highest_severity`, watch-edge `risk_level`, phase, and zone — not just whether smoke stayed green. Add focused projector tests for feed-only severity escalation and feed-only handoff/reboot phase/zone derivation before calling the slice review-ready.

Only (a) counts as fresh evidence, and even then a Codex-local Chromium startup error (for example `MachPortRendezvousServer ... Permission denied (1100)`) is an environment failure, not automatically a product regression. If you later rerun the same project wrapper command manually and it passes, the rerun is the stronger source of truth.
- Stronger stale-watch follow-up from the same batch family: Hermes can keep surfacing buffered watch notifications from an already-finished background Codex process long after the process has exited `0`, the slice PR has merged, the slice worktree has been removed, and local `master` is clean. - Stronger follow-up from MYC-174/175/176: Hermes can emit repeated background watch alerts from old buffered Codex output even after the underlying process has already exited 0 and the slice has since been manually revalidated. Before reacting to any later repeated watch alert, first re-check `process poll` / exit code and the on-disk worktree state. If the process is already complete and stronger evidence exists (local commit, manual rerun, green targeted validations), treat the repeated alert as stale notification noise rather than reopening the slice status.

Verify that the referenced worktree is gone or closed out, confirm open PR count is still zero / merged as expected, and then rerun that exact test selector on current `master` before escalating. Permission denied (1100)`, do not reverse-engineer the old child failure from the buffered alert. - New stale-completion rule from the April 2026 closeout loop: delayed system notifications for already-closed background review/smoke processes (`process poll -> not_found`) are not actionable by themselves. Before reacting, re-check live worktree list, current open PRs, and current branch cleanliness. Do not claim the broad suite is green, but do not hold the narrow slice hostage to an already-existing unrelated red either.
- Companion interpretation rule from the same batch: startup warnings like macOS `ThermalStateObserverMac unable to register to power notifications` or `DNS config watch failed to start` are weaker than a fatal browser-launch line and much weaker than a manual green rerun. Do not escalate those warnings into a slice red by themselves.
- Browser-smoke contract follow-up from MYC-176: when a new selected-agent canary depends on the active selected correlation, do not over-claim the whole transition window if the product legitimately performs an earlier unscoped read before the selected-agent default correlation settles. Name the canary around the settled contract (for example `once the selected-agent correlation settles`), and in assertions require the expected scoped request after that settling point instead of forbidding every earlier unscoped request. - In this pnpm workspace, do not assume `pnpm --filter <pkg> test -- --run <files>` will stay file-scoped; the package script may still end up running the full suite. - Safe rule: for real file-scoped validation in this repo, use `pnpm --filter @metaverse-office/web exec vitest run <files>` from the repo root, or `pnpm -C apps/web exec vitest run <files>` from the workspace root. - Browser-smoke teardown follow-up learned from MYC-151: if a new Playwright smoke uses `page.route(... route.fetch() ...)` around poll-driven refreshes and GitHub full preview smoke fails with errors like `apiResponse.json: Response has been disposed` or `route.fetch: Target page, context or browser has been closed`, do not misclassify that as a product regression first. Re-run the exact new smoke locally and, if it passes while the full suite red points at route callbacks firing during test teardown, apply the smallest test-only fix: explicitly `await page.unrouteAll({ behavior: 'ignoreErrors' })` before the test exits (or otherwise remove the route handlers) so in-flight late poll requests do not explode after Playwright starts closing the page/context.
- Additional pending-CI follow-up from MYC-204/205/206 closeout: when a PR is locally revalidated, independently reviewed, and GitHub still reports `MERGEABLE` while `statusCheckRollup.state` remains `PENDING`, do not stop at the aggregate status. Inspect the live Actions job steps for the current head SHA. If the active `push` / `pull_request` jobs are still sitting in early shared setup such as `Install Playwright Chromium`, treat that as remote CI provisioning wait rather than product regression, bad rebase, or evidence that another force-push is needed. Keep the slice in `PR-open / In Review`, keep Linear in `In Review`, and wait for those jobs to settle before merge decisions.
- Stronger remote-signal follow-up from PR #264: GitHub status sources can temporarily disagree. In the observed case, `mcp_github_get_pull_request_status` still returned `state: pending` with `total_count: 0` for head `4061718...`, while the live browser Checks tab already showed two real suites on the same PR head: `CI on: push` in progress and `CI on: pull_request` failed. Do not treat MCP aggregate `pending/0` as proof that no remote work exists. When aggregate status stays empty but a workflow file exists and multiple open PRs show the same symptom, cross-check the PR Checks tab or the concrete Actions run URLs before concluding the repo has no remote signal. Use the richer source to decide the next action: wait if a `push` run is still advancing, or investigate the concrete failed run if browser-visible checks already show a failure.
- Even stronger PR #264 remote-check follow-up: if the same PR head later shows `push` succeeded but `pull_request` failed, do not rewrite the slice branch immediately. First compare the slice diff against `origin/master`; if the failing surface (for example `apps/web` tests) is outside the slice diff, rerun the exact failing local test on the slice head and on clean `master`. If the same failure reproduces on clean `master`, classify the red as baseline/duplicate remote failure rather than slice drift, update the PR trail with that evidence, and do not touch the slice code again unless authenticated GitHub logs reveal a branch-specific blocker.
- Stronger duplicate-CI follow-up from the MYC-206 continuation: after force-pushing a refreshed sibling head SHA, GitHub can flip the aggregate `statusCheckRollup.state` to `FAILURE` as soon as one duplicate same-SHA `push` run fails in unit/integration, even while the matching `pull_request` run for that exact SHA is still alive and has already advanced through unit tests, typecheck, and build into browser-smoke steps. Do **not** treat that aggregate `FAILURE` as final truth and do **not** merge on optimism either. Re-audit the live Actions job details for both duplicates, treat the in-progress `pull_request` run as the primary source of truth while it is still advancing, and keep the slice in `PR-open / In Review` until that live PR run settles. If the stale sibling `push` run failed on a locally green exact test while the PR run is still progressing, record the duplicate-run situation in the PR/Linear trail instead of rewriting code prematurely.
- Additional duplicate-rerun closeout follow-up from the same MYC-206 batch: after rerunning only the failed duplicate `push` job on an otherwise locally green / PR-green same-SHA branch, do not trust the workflow-run aggregate timestamps as progress signals. GitHub can leave the rerun `workflow_run.updated_at` apparently frozen near rerun start while the replacement job is still legitimately moving through `web production build`, `browser smoke (preview)`, and long `browser smoke (dev)` steps. In that state, inspect the live rerun job steps (`actions/jobs/{job_id}`) and treat those step transitions as the source of truth. If the rerun job is still advancing and the only remaining work is the long smoke tail, keep the slice in `PR-open / In Review`, leave Linear in `In Review`, and wait; do not misclassify the branch as hung just because the run-level timestamp looks stale.
- Workflow fallback-correlation follow-up learned from MYC-153: when a smoke intends to prove a pivot falls back to an event-local correlation, do not reuse a correlation id that is already the destination agent's normal default, and do not forget earlier correlation seeds such as selected-operation state. Neutralize the pre-existing selected-operation correlation in test setup (for example by overriding the selected-operation read) and use a unique injected correlation id that only exists on the synthetic event. Otherwise the canary can look green while only re-proving the target agent's default path.
- Replay fallback-correlation follow-up learned from MYC-158: if a browser-smoke must prove a replay counterparty pivot falls back to the replay row's own correlation instead of the destination agent's default correlation, do three things together: (1) clear the pre-pivot active correlation to `No correlation selected.`, (2) inject a unique replay-only correlation id on a synthetic replay row instead of reusing the destination agent's shipped default, and (3) trap the stale/default correlation URLs with `page.route(...)`, enable that trap only at pivot time, then wait for the positive fallback requests and a short request-settle sample before asserting the stale/default correlation URLs never appeared. Positive-only assertions are too weak here; the UI can briefly hit the replay-row correlation and still regress back to the destination default later unless you guard the forbidden requests too.
- If edits accidentally land in the main repo worktree instead of the intended slice worktree, do not commit from main. Rescue them by exporting a patch from the dirty repo (`git diff --binary -- <files> > /tmp/<slice>.patch`), applying it inside the correct worktree (`git -C <worktree> apply /tmp/<slice>.patch`), then restoring the main repo (`git restore -- <files>`). Re-check both locations before continuing so `master` stays clean.
- Closeout hygiene follow-up from the MYC-180/181/182 batch: Hermes/Codex prompt files under a slice-local `.hermes/` directory are untracked and can block `git worktree remove` with `contains modified or untracked files`. Do not misclassify that as unfinished product work. First confirm the slice is already merged / fast-forwarded and local `master` is clean, then either delete the slice-local `.hermes/` directory if safe or use `git worktree remove --force <worktree>` during closeout. Treat this as cleanup noise, not as a reason to reopen the slice.
- For uncommitted slice review, `origin/master...HEAD` may be empty even though the worktree is dirty. In that case, review `git diff origin/master -- <files>` or explicitly tell Codex to review the working-tree diff rather than committed history only.
- Stronger follow-up learned from MYC-96/97/98: after Codex or Hermes fixes a review finding but leaves the branch dirty, do not trust a second review prompt that only says `origin/master...HEAD` — it can re-review the stale committed diff and miss the new working-tree fix. Re-run independent review with wording like `INCLUDING uncommitted working-tree changes against origin/master`, or review `git diff origin/master` directly, before declaring the slice review-approved.
- Companion delivery rule from the same batch: if a review-blocked slice is repaired locally and the fix is still intended to ship as one logical slice, amend the existing slice commit (`git commit --amend --no-edit`) after the targeted validation passes instead of stacking a noisy follow-up commit. Then re-run the targeted smoke/canary and the independent review on the amended state before push/PR.
- Accessibility/status follow-up learned from MYC-99: if a slice surfaces stale/unavailable runtime state in a header/stat card, do not hide the real error detail in `title` or plain passive text. Use an explicit `role="status"` (or equivalent announced status semantics) and keep the visible text rich enough to expose both the state label and the failure detail. Add tests that assert the status role/text, not just a visible word like `Unavailable`.
- Selected-agent polling follow-up learned from MYC-100: when adding a new selected-agent polled resource with `usePolledResource`, do not pass raw `resource.data` straight into the Details panel. `usePolledResource` keeps the previous successful payload until the new effect clears, so switching from agent A to agent B can briefly render A's data under B. Wrap the payload with its selection key (for example `{ targetAgentId, alerts }`), guard it against the current `selectedAgentId`, and if the loaded payload belongs to the previous agent while the new fetch is pending, coerce the surfaced state back to `loading` and suppress stale error text until the matching payload arrives. Add an App-level test that delays the second agent's response and proves the first agent's record disappears immediately after the pivot.
- Stronger selected-agent replay follow-up learned from MYC-206: apply the same stale-payload rule to newly added selected-agent replay resources, not just supervision history. If a slice introduces canonical selected-agent `/timeline?agent_id=...` polling, do not feed raw replay `usePolledResource.data/error/state` straight into `DetailsPanel`, or the UI can briefly show the previous agent's replay snapshot under the new selected agent after a pivot. Safe pattern: wrap the replay payload with the current `targetAgentId`, track the current replay resource key, treat a key change or mismatched payload agent as stale, surface `loading` with `null` data/error until the matching replay payload arrives, and only then show the new replay snapshot. Required regression coverage: after filtering selected-agent replay for agent A, pivot to agent B while delaying B's replay response, assert agent A's replay row disappears immediately, the replay section shows the truthful loading copy for B, and only after the delayed response resolves does B's replay snapshot render.
- Additional selected-agent replay request-scope follow-up from the same MYC-206 closeout: guarding the canonical selected-agent replay poll with `workflowResource.state === 'loading'` (or `idle || loading`) is not sufficient. On a fresh selected-agent pivot, one render can still have `selectedCorrelationId === null`, `defaultCorrelationId === null`, and no resolved selected-agent workflow yet while other carried context (for example an operation snapshot) makes the old pending predicate look false, which allows an early unscoped `/timeline?agent_id=...` request before the default correlation is known. The safer gate is semantic, not phase-name based: if the selected-agent path is not explicitly preserving null correlation, and `selectedCorrelationId` plus `defaultCorrelationId` are still null while `activeWorkflow === null` and `workflowResource.error === null`, treat the default correlation as still pending and do not start the selected-agent canonical replay poll yet. Add a focused App-level regression that stubs the selected-agent workflow request to hang, pivots into the agent, and asserts both `correlationRequests === 0` and `selectedAgentReplayRequests === 0` until the workflow/default-correlation path resolves.
- Stronger split-gating follow-up from the MYC-206 rebase fix: do **not** reuse that stricter selected-agent replay pending gate for selected-agent supervision history. In this repo, replay must sometimes wait for workflow/default-correlation resolution so canonical `/timeline?agent_id=...` does not fire early, but supervision history still has an older seeded target-agent contract and may need to request `/peer-watch/alerts?target_agent_id=...` before workflow correlation settles. If you share one `selectedAgentDefaultCorrelationPending` boolean across both resources, a replay hardening change can silently block supervision-history requests and only show up later as a browser-smoke timeout waiting for `/peer-watch/alerts?target_agent_id=<agent>&limit=4`. Safe pattern: keep separate pending predicates per resource (`selectedAgentTimelineReplayDefaultCorrelationPending` vs `selectedAgentSupervisionHistoryDefaultCorrelationPending` or equivalent) and add a regression proving the split: with workflow/default-correlation still hanging, selected-agent replay stays blocked (`selectedAgentReplayRequests === 0`) while supervision history still issues the seeded target-agent peer-watch request.
- Selected-agent supervision-history filter follow-up from MYC-211: when adding a new selected-agent-local filter to a `usePolledResource` surface (for example supervision-history severity), do not feed raw `resource.data/error/state` into `DetailsPanel` after the filter enters the resource key. `usePolledResource` only clears stale data in an effect after one render, so the combobox can show the new severity while the old unfiltered peer-watch rows are still visible. Safe pattern: wrap the payload with every semantic key that affects the request (`targetAgentId`, `correlationId`, `severity`, plus the response), track the previous resource key, treat key changes or mismatched payload keys as stale, and surface `loading` with `null` data/error until the matching payload arrives. Required regression coverage: delay the filtered request, select the filter, assert the old row disappears and severity-specific loading copy appears before resolving the new response, then assert the new filtered row renders.
- Incident-feed retry follow-up learned from MYC-99: if a resource backed by `usePolledResource` is rendered in more than one surface (for example a header stat and the Hub details panel), do not fix retry/loading semantics in only one consumer. `usePolledResource` can set `state` back to `loading` on a retry before first successful data while still retaining the previous `error` until the request resolves. If one surface is changed to prefer `loading` over stale `error`, audit every sibling surface consuming the same `state`/`error` pair and keep them semantically aligned; otherwise the header can announce `Feed · Loading` while the Hub still shows the old error. Add a regression that covers the pre-data retry window across both surfaces, and hide stale error text during that loading retry instead of presenting contradictory states.
- Correlation-reset follow-up learned from MYC-101: for a `Return to current scope` / manual-correlation-reset action, do not blindly call `onSelectCorrelation(null)` if other resources (especially shared-memory artifacts) key directly off `selectedCorrelationId`. That creates a transient unscoped request window before auto-selection restores the default correlation. Instead add a dedicated reset handler in `App` that computes the next default correlation immediately from the current selected-agent/operation/workflow/incident context and sets the correlation state atomically to that scoped value while also switching the selection mode back to `auto`. Add an App-level request-slice assertion that the post-reset fetches include the expected scoped URL and explicitly exclude the unscoped fallback URL.
- MYC-104 follow-up: do not conflate `manual correlation override` with `carry this already-selected correlation forward through the next agent pivot`. They are different semantics. If one boolean drives both reset-CTA/scoped-replay UI and workflow-counterparty correlation carry, you can make the default-correlation auto-reselect tests pass while still breaking browser-smoke preserved-correlation pivots. Keep separate state/derived signals: one for manual-override UI (`Return to current scope`, scoped replay copy), another for whether the current selected correlation should still be preserved across the next workflow/accountability counterparty pivot.

Cover the accountability-style current-correlation reselect path too; jsdom-only auto-reselect assertions are insufficient because keyboard/browser smoke can still drop back to the target agent default or a no-correlation path.

In practice for this repo, incident-correlation buttons and selected-operation/current-operation correlation buttons may opt into `preserveAutoOnDefaultReselect`, but workflow/workflow-status/accountability reopen buttons must stay explicit reopen paths. Then rerun both sides of the matrix: auto-no-op tests for crew-overview/selected-agent current-scope buttons, and browser-smoke canaries for workflow/accountability reopen paths that must remain explicit.

- For those pivot-enrichment slices, do not stop at a component test that only checks `onSelectAgent(...)` arguments. Add an App-level integration test that proves the preserved correlation survives the pivot and drives the expected follow-up fetch/resource key on the destination agent surface.
- Selected-agent replay follow-up from MYC-182: if you add a replay lane inside selected-agent details, do not widen the request surface by reusing the global `/timeline?correlation_id=...` feed just because an active correlation exists. In this repo, the selected-agent lane must stay target-agent scoped: use `workflow.timeline` for the unscoped selected-agent case, and when a correlation is active reuse `correlation.timeline` filtered to `event.agent_id === selectedAgent.agent_id` rather than fetching correlation-wide replay.
