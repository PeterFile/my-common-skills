# SkyTurn `demo:mvp` validation pattern

Use this when validating SkyTurn natural-flow / Hermes-to-Codex runtime paths.

## Problem class
`pnpm --filter @skyturn/desktop run demo:mvp` is a real agent-driven acceptance path, not a quick unit test. It may exceed a foreground tool timeout while still making progress through Hermes planning, Codex implementation, validation, screenshot, review, and commit lanes.

## Practical validation pattern
1. Run the normal build/lint/typecheck/test gates first so TypeScript/project-reference regressions are caught cheaply.
   - If `better-sqlite3` was rebuilt for Electron, Node/Vitest persistence tests may fail with `NODE_MODULE_VERSION` mismatch. Rebuild the package for the current Node ABI before Node tests, then run `@skyturn/desktop rebuild:native` last before Electron/demo validation. Keep this as an execution ordering fact, not a product-code bug.
2. If code under `@skyturn/ui-canvas` changes and the desktop demo imports that workspace package through its compiled export, rebuild it explicitly before the demo: `pnpm --filter @skyturn/ui-canvas run build`. Verify the package as the desktop app resolves it, not from the monorepo root; package resolution can differ by caller.
3. For `demo:mvp`, do not infer failure from a foreground timeout alone. If it can exceed the tool's foreground limit, start it as a managed background process and poll/wait for the final exit code.
4. If the full demo appears silent, first poll the managed process and inspect the process tree. The script may print nothing until final JSON while child Hermes/Codex lanes are still active in a temp repo. If repo-local `.devflow/runs/*/events.ndjson` is absent, locate the temp project from the child command line before concluding there are no events.
5. A one-run diagnostic (`SKYTURN_DEMO_MAX_RUNS=1`) is useful only to prove the Hermes planner creates a graph. It is expected to exit non-zero because downstream lanes were intentionally skipped; do not report it as full acceptance.
6. Treat screenshot/browser evidence as stronger than source-string validation. Source grep may pass while Vite/browser rendering fails. Intermediate lane summaries can report blockers that a later commit/repair lane is allowed to fix; do not stop on those summaries while the demo process is still running. Let the demo reach terminal state, then verify the final JSON has `"ok": true`.
7. Record the final JSON facts, especially: `ok`, `testExitCode`, `screenshotPath`, `screenshotBytes`, `commitCount`, `gitStatus`, changed files, card statuses, graph connectivity, duplicate semantic keys, dependency mismatches, and run evidence exit codes.

## Demo-specific implementation checks
- The temporary React app must resolve runtime/browser dependencies (`vite`, `electron`, `react`, `react-dom`) from a package that actually declares them, usually `apps/desktop/node_modules`, not the monorepo root `node_modules` when the root package only declares tooling like Turbo.
- Screenshot/browser lanes create repo-local artifacts such as `.devflow/acceptance/react-app.png` and may need to launch local Vite/Electron/Chrome. If the workflow projection marks such a lane `read-only`, route the exception through the centralized `sandboxForNodeRun` policy and grant `danger-full-access` only for browser/screenshot lanes; do not loosen ordinary validation lanes. `workspace-write` can still block local listener/browser processes even though it allows file writes.
- Commit lane prompt/sandbox policy must use trusted workflow projection fields, not free-text titles. Prefer canonical `CanvasNode.laneKind === "commit"`; fall back only to trusted legacy metadata when no canonical field exists. Do **not** grant commit instructions just because a non-commit lane title contains “commit” — that lets implementation lanes create commits. If materialization drifts (for example display meta says `implementation` while the lane is semantically commit), fix the projection/materialization to carry canonical `laneKind: "commit"` and add both positive and negative regression tests.
- After changing centralized runtime policy or prompt classification in `packages/ui-canvas/src/workflowRuntime.ts`, rebuild `@skyturn/ui-canvas` before retrying the desktop demo because the demo imports compiled workspace output. Verify the policy from the desktop package resolution context, not from the monorepo root.

## Pitfalls
- A foreground timeout or explicit `process.kill` can hide a still-running Codex or Hermes lane. Check the process tree and per-lane temp repo evidence before killing or declaring failure. If you do kill a run, report it as killed/unknown, not as acceptance failure or success. After a timeout/kill, clean up orphaned `mvpWorkflowDemo`, Hermes/Codex, Vite, and temp-repo processes before retrying so the next run is not contaminated.
- A lane may correctly surface a temporary blocker such as missing screenshot dependencies, then a later lane installs/repairs/commits and final JSON succeeds. Final acceptance comes from the demo process exit code and final JSON, not from an earlier child-agent summary.
- `demo:mvp` can exit non-zero even when all individual lane run evidence says `exit 0`. Read the final JSON `ok` inputs before diagnosing: `commitCount`, `changedFiles`, `gitStatus`, graph facts, and screenshot bytes identify which acceptance predicate failed. Dirty files plus `commitCount` unchanged usually means the commit lane did not commit; inspect its generated prompt before touching git logic.
- Demo temp repos may use symlinked `node_modules`; browser/screenshot lanes can uncover dependency-resolution, Vite cache, Electron, or React runtime issues that unit tests miss. Link temp app `node_modules` to a package that actually declares `vite`, `electron`, `react`, and `react-dom` (for SkyTurn, `apps/desktop/node_modules`), not a root package that only declares orchestration tooling.
- If a PR body was created while the demo was still running, update the PR after the background demo completes. Do not leave stale text saying validation is pending when `ok: true` is already known.
